Design Decisions

Why Mellis is designed this way

Immutable by default

Context: Systems languages often suffer from accidental mutation and hidden side effects.

Decision: Prefer immutability unless mutation is explicitly requested.

Alternatives: Fully mutable-by-default semantics or pervasive reference mutation.

Trade-offs: Better clarity and reasoning at the cost of occasional explicitness.

Status: Intended design direction.

Ownership + borrowing

Context: Memory safety must be explicit enough for systems code but not hostile to ergonomics.

Decision: Model memory through ownership and borrowing, with compiler checking.

Alternatives: GC-only, RAII-only, or manual pointer-heavy systems.

Trade-offs: Stronger safety guarantees, but more discipline in code design.

Status: Core semantic direction.

Inferred lifetimes

Context: Borrow checking becomes hard when lifetimes are always spelled out.

Decision: Use inference to reduce user burden while preserving compiler safety.

Alternatives: Full explicit lifetime annotations everywhere.

Trade-offs: Cleaner syntax, but more complex compiler reasoning.

Status: Under active design refinement.

Traits instead of inheritance

Context: Inheritance mixes identity, behavior, and hierarchy in ways that become fragile.

Decision: Favor trait-based abstraction for extensibility and polymorphism.

Alternatives: Class inheritance or interface-heavy OO modeling.

Trade-offs: Better composition and specialization, but requires trait resolution machinery.

Status: Planned feature set.

Monomorphization

Context: Generic code should avoid runtime overhead and remain predictable.

Decision: Use monomorphization for code generation and specialization.

Alternatives: Dynamic dispatch or runtime type erasure.

Trade-offs: High performance and predictable code, but more compile time and binary growth.

Status: Supported in the compiler architecture.

MVIR

Context: Direct LLVM generation can become unmanageably coupled to frontend semantics.

Decision: Introduce an explicit virtual intermediate representation before LLVM lowering.

Alternatives: Emit LLVM IR directly from the AST or fork many passes into the frontend.

Trade-offs: Better pass separation and more stable compiler pipeline, with extra engineering work.

Status: Core infrastructure in progress.

.mlib packages

Context: Recompiling the full standard library on every change is costly and rigid.

Decision: Package reusable library components into .mlib artifacts with metadata and loader support.

Alternatives: Source-only libraries or ad hoc linker scripts.

Trade-offs: Faster reuse and modularity, but more metadata and packaging discipline.

Status: Planned and partially implemented.

Backend independence

Context: The language should not become an LLVM-only design by accident.

Decision: Keep backend concerns behind MVIR so code generation can change without reworking core semantics.

Alternatives: Directly tie the language to one backend or one target family.

Trade-offs: More abstraction, but better portability and future targets.

Status: Architecturally intended.

No GC by default

Context: Systems programming is sensitive to runtime unpredictability.

Decision: Favor explicit memory models and deterministic ownership rules over a garbage collector.

Alternatives: Traditional GC semantics or hybrid garbage-collection approaches.

Trade-offs: More control and performance, but more compiler responsibility for safety.

Status: Core platform decision.
