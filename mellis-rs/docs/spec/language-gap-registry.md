# Luna Language Gap Registry (SSOT)

This document serves as the canonical registry for known, audited, intentional language gaps in the Luna compiler. Gaps documented here are not accidental oversights or undefined behavior; they are explicitly characterized boundaries between the currently supported language surface, unapproved syntax/semantics, and deferred capabilities.

New language features must be prioritized based on empirical blockers discovered during real software development (e.g., in `REAL-WORLD-01`), rather than speculative parity with foreign languages.

---

## Active Gap Registry

| Gap ID | Subsystem | Title / Capability | Status | Disposition & Rationale |
|---|---|---|---|---|
| **LANGUAGE-GAP-01** | `luna-borrowck` / `luna-semantic` | Borrowed enum payload projection | Documented & Deferred | Pattern-matching borrows into enum variant payloads (`match &val { Option::Some(&x) => ... }`) require first-class reference projection through variant tags. Currently, value-matching and moves are supported, while borrowed variant projections are deferred. |
| **LANGUAGE-GAP-02** | `luna-parser` / `luna-semantic` | Range expression syntax sugar (`..`, `..=`) | Documented & Deferred | Native token-level syntax sugar for half-open (`a..b`) and closed (`a..=b`) ranges is not yet parsed into standard library `Range<T>` objects. Range iteration is currently achieved via explicit loop indexes or explicit iterator structs. |
| **LANGUAGE-GAP-03** | `luna-semantic` / `luna-mvir` | Open-generic-dependent comptime under current pre-mono staging | Documented & Bound by Phase Order | Under the current pre-monomorphization staging model, comptime blocks depending on open generic parameters (`comptime { sizeof(T) }` or `comptime { x }` where `x: T`) are rejected with `E_UNRESOLVED_PROJECTION`. Type-independent comptime in generic contexts is supported; generic-dependent comptime would require a staged or post-monomorphization evaluation model. |
| **LANGUAGE-GAP-04** | `luna-semantic` / `luna-borrowck` | Borrowed/lending iterator item lifetime expressiveness | Documented & Deferred | Inability of the current trait and lifetime signature system to express lending iterator protocols where `Iterator<Item = borrowed view tied to iterator/source lifetime>`. Standard library collections (e.g. `String::split`, `String::lines`, `String::split_whitespace`) return owned `Vec<String>` allocations (`SUPPORTED-WITH-OWNED-RESULT`) for v1, which is a soundly supported v1 API avoiding generic associated types (GATs) or lifetime-parameterized trait contracts, while borrowed/lending variants remain tracked in this registry. |
| **LANGUAGE-GAP-05** | `luna-semantic` / `luna-borrowck` | Borrow-carrying aggregate lifetime parameterization | Documented & Deferred | A by-value aggregate cannot currently parameterize and transitively expose borrowed provenance originating from an external lifetime domain. Demonstrated empirically by the HashMap `Entry` API probe, where an enum variant holding `&rw V` or `(&rw HashMap<K, V>, K)` cannot propagate its borrowed lifetime through method returns (`life_from(self)`) without aggregate lifetime parameterization. Standard library collections adapt by providing direct insertion fallbacks (`get_or_insert`, `insert_if_absent`) for Phase 4B. |

Public Stdlib Contract (Frozen ✅)*:<br>- Luna exposes **NO** public `process::*` namespace (and no duplicate aliases like `env::args`, `sys::args`, or `runtime::args`).<br>- Process startup and argument acquisition are runtime and compiler concerns, not stdlib abstractions. ## Architectural Principles for Gap Prioritization

1. **Evidence-Based Prioritization**:
   Language capabilities transition from `LANGUAGE-GAP` to active implementation only when driven by concrete friction in real software:
   $$\text{Real-world software development} \longrightarrow \text{Documented blocker} \longrightarrow \text{Minimal language contract} \longrightarrow \text{Compiler implementation}$$
2. **Phase-Order Sanctity**:
   Capabilities that conflict with the established phase ordering:
   $$\text{Parse} \to \text{Import} \to \text{Macro} \to \text{Resolve} \to \text{Typecheck/Comptime} \to \text{Mono} \to \text{Borrowck} \to \text{MVIR} \to \text{LLVM}$$
   must remain `UNSUPPORTED BY DESIGN` rather than breaking compilation invariants.
3. **No Unapproved Syntax**:
   Syntactic sugar (such as range literals) must be formally approved in `mellis-grammar` before any parser or AST changes are introduced.
